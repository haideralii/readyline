# data/

Source-of-truth fixtures for the standards mapping (REQ-001).

- `sources/`: verbatim text snapshots of the NDIS Quality and Safeguards
  Commission pages and PDFs (and the legislation register's table of contents)
  the mapping is built from, with `manifest.json` recording each URL, fetch
  date and SHA-256. Never edit these by hand; re-fetch and diff instead.
- `standards.meta.json`: hand-maintained inputs that are not Commission text:
  the source list, module inventory and which snapshot each module is parsed
  from, registration groups with their audit type and modules, derivation
  rules, and our draft evidence guidance per standard.
- `standards.json`: generated by `npm run standards:build`. Outcomes and
  quality indicators are parsed from the snapshots, so the dataset is diffable
  against what the Commission published. Do not edit by hand.
- `SOURCES.md`: generated alongside, lists every source with its hash, the
  dataset contents, the `UNVERIFIED` items and the changelog.
- `standards.test.ts`: tests over the built dataset (counts, group mapping
  invariants, rule sources, hash agreement, indicator order).

Commands:

```bash
npm run standards:build            # regenerate standards.json and SOURCES.md
npm run standards:verify           # fail if any snapshot hash drifted (runs in CI)
npm run standards:report -- 0120 0107   # modules, pathway, reasons, draft evidence
```

The schema lives in `src/lib/standards/schema.ts`, the derivation in
`src/lib/standards/derive.ts`, the parser and builder in `scripts/standards/`.

## Refreshing a snapshot when the Commission changes a page

This is the procedure to follow, in order, when a Commission page or PDF has
changed (CI's `standards:verify` will not notice a change on the website by
itself; it only guards the files in this repo).

1. Download the page or PDF again with a browser user agent (the site times
   out for plain fetchers; see DECISIONS D-110) and reduce it to text the
   same way as before: HTML main content with tags stripped and `<h2>`/`<h3>`
   headings kept, PDFs via pypdf with page markers. Overwrite the file under
   `sources/` with LF line endings.
2. `git diff data/sources/<file>.txt` and read every changed line. Decide
   whether the change is editorial (typo, link) or substantive (new or
   reworded outcome or indicator, new class, new date). Substantive changes
   need a `DECISIONS.md` entry and may need questionnaire or document changes
   in other REQs.
3. Update that file's `sha256`, `bytes` and `fetchedAt` in
   `sources/manifest.json`. If the Commission shows a new version label or
   effective date, update the matching entry in `standards.meta.json` too.
4. Bump `version` in `standards.meta.json` (patch for editorial, minor for
   substantive, major if the shape of a module changes), set `generatedAt`
   and `checkedAt` to today, and add a changelog line saying what changed.
5. If a standard's indicators were reordered, do not let the index silently
   move: keep the published order stable by appending, or bump the major
   version and record it (the indicator ids `<standardId>#<index>` are used by
   self-assessments).
6. `npm run standards:build`, then `npm run standards:verify`, then
   `npm test`. The build fails if a module no longer parses to the expected
   number of standards (`expectCount` in the meta file); fix the meta file or
   the parser, never the snapshot.
7. Commit the snapshot, manifest, meta, generated files and decision together
   so the diff tells the whole story.
