# QA lead

Haider is a QA engineer: tests here are first-class, written before or with the code, and they prove behaviour rather than decorate it. The product owner reviews against `product/qa/definition-of-done.md` and `product/qa/review-checklist.md`; this skill makes sure nothing in those documents is missed.

## Test strategy for every REQ

Before implementation, write a short test plan in the REQ's Dev response:

1. **Map each acceptance criterion** to one or more tests by level (unit, integration, e2e, manual). An AC with no automated test needs a written reason and a manual test record.
2. **Risk-rank** the feature: what breaks a provider's audit preparation, leaks data, charges money wrongly, or produces a prohibited claim? Those paths get the most tests and negative cases.
3. **Choose techniques** deliberately: equivalence partitions and boundary values for inputs (lengths, dates, counts of workers, number of registration groups); decision tables for rules (audit pathway, entitlements, reminder timing); state transitions for subscriptions and questionnaire progress; pairwise for combinations of registration groups and business structures.
4. **List negative and edge cases** the REQ did not mention: empty, maximum, unicode and emoji in text, leap day, DST change, two tabs open, double submit, back button mid-flow, expired session mid-form, webhook replay, refund after download.
5. **Decide fixtures**: deterministic, region-agnostic, no real provider or participant data, generated by small factory helpers in `src/test/`.

## Levels and tools

- **Unit (Vitest, jsdom)**: pure logic in `src/lib/**` and `data/**`: standards mapping, derivation rules, claims checker, validation schemas, entitlement derivation, date maths, document assembly, redaction. Every branch in rules code is covered (DoD item 2). Snapshot tests only for generated document structure, reviewed on every change, never auto-accepted.
- **Component (Vitest + Testing Library)**: components with conditional logic. Query by role, label and text; test ids only when no accessible handle exists (that itself is an accessibility finding).
- **Integration**: route handlers, server actions, RLS and migrations against a local or test Supabase; Stripe webhooks with fixture events; generation pipeline with recorded model responses.
- **End-to-end (Playwright)**: user journeys on `desktop-chromium` and `android-small`. Production build in CI (`next start`), dev server locally. One spec file per journey under `e2e/`, page objects only when a flow is reused by three or more specs.
- **Manual**: screen reader pass, real-device check on an Android phone for each new screen before a phase gate, exploratory session per REQ with notes.

## Writing good tests

- Name tests as behaviour statements: `shows a validation error when ABN has 10 digits`, not `test ABN`.
- One behaviour per test; arrange, act, assert visible. Avoid shared mutable state and order dependence; each test creates what it needs.
- Prove the test can fail: when adding an assertion, break the code once (or mutate the expected value) and watch it go red before fixing. Note "proved failing" for rule-code tests in the evidence.
- Assert outcomes users see or data that persists, not implementation details. Avoid asserting on class names, internal function calls or exact copy that is likely to be edited (assert on key phrases or roles instead).
- Playwright: web-first assertions (`expect(locator).toBeVisible()`), no `waitForTimeout`, no `networkidle` as a crutch; `test.step` for long flows; trace on first retry; screenshots on failure retained as artefacts.
- Tag by purpose: `@smoke` for the five-minute pre-release run, `@a11y` for accessibility specs, `@payments` for Stripe test-mode flows.
- Keep tests fast: unit suite under 10 seconds, e2e under 5 minutes in CI; parallelise, do not sleep.

## Domain-specific checks that must exist

- **Standards mapping**: every registration group maps to at least one module; verification groups map to the verification module only; mixed groups resolve to certification; SDA-only, modified-certification and restrictive-practice rules each have a decision-table test; every standard has a source and a verification status; unverified records carry a note; source hashes match the manifest.
- **Claims**: `findProhibitedClaims` runs over all site copy fixtures and every generated document in tests; a prompt-injection fixture set must not alter document structure or introduce claims.
- **Privacy**: register fields are length-capped; a participant-data detector test (names, dates of birth, NDIS numbers, addresses) warns; register text never appears in prompts or emails (assert on the captured payloads).
- **Payments**: entitlement only after a verified webhook; replayed event is ignored; tampered signature rejected; past-due pauses without penalty copy; refund revokes.
- **Accessibility**: automated axe scan (via `@axe-core/playwright` once added) on every new page in both projects with zero serious or critical violations; keyboard-only traversal spec for the main journey; focus returns after dialogs.
- **Security headers and CSP** (from REQ-002): header values asserted on `/`; no `securitypolicyviolation` events during the smoke journey.
- **Mobile**: no horizontal overflow at 360px; tap targets at least 44px (assert bounding boxes on primary controls).

## Flaky and failing tests

- A red CI is a stop-the-line event. Do not retry-until-green; find the cause. Common causes here: missing `await`, asserting before hydration, time-dependent data without a fixed clock (use `vi.useFakeTimers` or Playwright's `clock`), parallel tests sharing an account, Cache Components serving stale data in a test that expects fresh.
- Quarantine only with a linked issue, an owner and a date; never delete a failing test to make CI pass.
- Record flaky-test root causes in `DECISIONS.md` if they change a convention.

## Evidence pack (what the PO expects in "Delivery evidence")

```
### Test evidence
- AC mapping table: AC id, test file and name, level, status
- `npm run check` output (lint, format, typecheck, unit) and `npm run test:e2e` summary
- CI run link or log excerpt (green on the branch)
- Screenshots at 360px and desktop for each new state
- Accessibility: axe results, keyboard pass notes, screen-reader pass notes
- Negative and edge cases executed (list), with any defects raised
- Flaky or quarantined tests (should be none) with links
- Anything UNVERIFIED or deferred, with the reason
```

## Reviewing someone else's tests

Ask: can this test fail? Does it assert behaviour or implementation? Is the data region-agnostic and free of real people? Is there an order dependence? Are negative cases present? Would the AC be satisfied if this test passes? If the answer to any is wrong, request changes with the AC or DoD line it violates.

Related skills: `frontend-dev` and `backend-dev` for implementation conventions, `cyber-security` for abuse cases to add to the plan, `release-gate` for the pre-ship run.
