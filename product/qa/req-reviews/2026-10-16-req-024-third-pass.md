## 1. Testability

56. AC-6: "when it updates `confirmed_on` on its own item, then the write is refused with 42501". SR-2 lets a worker "update only `done_on`, `number` and `expires_on` on their own `onboarding_items` rows, never `confirmed_on`". A row policy cannot see the old row or name columns, and a column-level grant (the D-2241 pattern) is per database role, and the owner and the worker are both `authenticated`, so nothing in the REQ's data design can produce a 42501 on one column for one role. Fix: SR-2 and Data say how: a `before update` trigger on `onboarding_items` that raises 42501 when `public.is_worker(account_id)` and `new.confirmed_on is distinct from old.confirmed_on` (and the same for `owner_role`), or the worker's writes go through one `security definer` function that takes the three fields only; the integration test then has something to assert.
57. SR-2 and AC-3: "a worker may insert their own ticks". On `main` `onboarding_ticks_insert_subscribed` requires `public.is_member(account_id)`, and since REQ-020 Session B `is_member` means owner or member only (`20261015050000_worker_role_and_report_links.sql`), so a worker's insert is refused today; the same holds for the worker's read of their own `onboarding_checklists` row and `staff_matrix` row (select policies are `is_member`), which FR-7's "their own list" needs for the role, states and flags. Fix: SR-2 lists every new `is_worker` policy by table (select on the worker's own `staff_matrix`, `onboarding_checklists`, `onboarding_items`, `worker_clearances` and `policy_acknowledgements` rows by `worker_ref = memberships.worker_ref`; insert on `onboarding_ticks` with `ticked_by_ref` equal to that code; insert on `policy_acknowledgements`), each under the subscription gate as REQ-020's worker policies are, so the integration suite has a fixed list.
58. AC-13 and FR-6a: "reconstructable for any day in the last seven years from the rows and the trail (s 20)". `staff_matrix` is one mutable row per worker; `risk_assessed`, `role_ref` and `role` change in place, and `register_events` holds a free-text `note` (1000 characters, no structured old or new value). A worker who was reclassified from admin to support worker on 2025-03-01 has no dated fact that says which days they were in a risk assessed role, and AC-13's inputs (a start date and an end date per worker) cannot catch that. Fix: Data gives role membership dates (a `risk_assessed_from date` set when the flag turns true and cleared into the trail when it turns false, or a `role-changed` event whose `note` is a fixed `from=<code> to=<code>` the builder parses), and AC-13 gains "W-2 reclassified into a risk assessed role on 2025-03-01: absent for 2025-02-01, present for 2025-03-02".
59. AC-2, AC-4, AC-14 and FR-2a's six-month rule turn on "today" with no fixed clock: the derived state "reads a supervisor's row daily", AC-14 says "read after it", AC-4 "expiring in 30 days", and Data says `state-screening.json` is "read at build time", so a deploy older than six months would keep a stale state fact alive and the test could not show it. Fix: every derivation takes a `today` in Australia/Sydney (the D-2242 rule), the staleness is judged at request time against the read date, and each AC names its clock ("today 2026-11-01").
60. FR-9 and AC-8: "the worker's first three steps in plain words". The list is derived per worker (FR-2), so "three steps" has no fixed content, and the e2e cannot assert them. Fix: FR-9 names them ("the Code of Conduct acknowledgement, the orientation module, the mandatory policies": W-3, W-4, W-6, the three every worker has) or says "the first three items of the worker's own list in W order", and AC-8 asserts those strings.

## 4. Privacy and security

76. FR-6b, SR-8(b) and the export limiter: the fill form is "cleared on download, navigation or after ten minutes", and every export route shares `checkRegisterExportAllowed` (five an hour per account, `src/server/auth/rate-limit.ts`), which the pack and the link already spend. An owner who types eight workers' names, dates of birth and addresses on a phone and meets a 429, or the ten-minute clock, loses the lot and types it again, which trains the owner to keep the details in a text file next to the browser, the one place the REQ's controls do not reach. Fix: the three fill routes share one limiter slot per download set (or sit outside the register limit, stated), the clock runs from the last keystroke, and the 429 path returns the form with its values still in the page (never stored) and a plain message.

Fix: FR-6b says the filled worker-file download is one zip of the `workers/` folder from one submission, and the per-worker page's export is unfilled.
78. FR-11 and Scope: Scope puts "a worker's performance notes" out, FR-11 adds `supervision_entries` with a "probation review" kind and a 500-character note "with the participant warning". A probation review note is a performance note about a named-by-code worker, personal information the worker's home never shows (finding 40(b) is open) and the one new free-text field about a person this REQ adds. Fix: the note's helper says "what was covered, not how the worker performed" and the kind "probation review" records a date and an outcome code (continued, extended, ended) with no note, or Scope admits performance notes and the lawyer's 40(b) is answered first.
