# REQ-022: Launch readiness: the switchboard, the email provider, the domain, and the lawyer's bundle

Status: ready (PO, 15 Oct 2026; written from the launch blockers in the product status of 15 Oct, `supabase/ops/DEPLOY.md`, `.env.example`, REQ-004 FR-7, REQ-007, REQ-008, REQ-010 and D-013; Session A delivered; the independent review of 15 Oct 2026 is in `product/qa/req-reviews/2026-10-15-req-022-023-024.md` and the PO's decisions on it are applied to this text before Session B, which waits for Haider's SES confirmation)
Phase: 6 Priority: must Owner: Dev

## Why (user and business outcome)

Everything a customer pays for is built and on production, and the product still cannot take a real payment, send a real email or be reached at its own name. The gap is a set of environment changes, account steps that only Haider can take, and checks that nobody has written down as code. This REQ turns that list into dev work so that, when the ABN, the Stripe live keys, the domain and the email key exist, going live is one pass through one page with every line green, and never a guess about which variable is missing. It also makes the "is it safe to be live" question answerable by a test, which is what a sole trader selling compliance documents owes the people who buy them.

## Scope (in / out)

In, as four sessions:

- Session A, the launch switchboard: an admin page and an ops script that show the state of every launch condition, by name and never by value, and the guards that refuse a half-configured live mode.
- Session B, transactional email: the provider behind `createEmailProvider()` (D-013 closes with D-2201), the sending domain, the magic link through the same provider, and the register reminders going out for real.
- Session C, the domain: the custom domain on Vercel, every URL that must change with it, the redirect from the vercel.app name, and the smoke test run against the real name.
- Session D, the lawyer's bundle and the business identity: one export of everything a lawyer reads, the ABN and business-name switch exercised end to end, and the About page's name.

Out: Sentry (REQ-010 part 2, its own item); a status page; marketing pages; any change to prices or plans; the recording session (its own runbook, `product/evidence/req-005/`); anything that reads a secret value into a page, a log or a file.

## Functional requirements (numbered FR-1 ...)

Session A, the launch switchboard

- FR-1 `/admin/launch` (behind `requireAdmin()` and the TOTP step, REQ-004 FR-7) lists every launch condition as a row with a name, a state (set, unset, mismatched, unverified) and one plain sentence on what to do, grouped: identity (BUSINESS_NAME, BUSINESS_ABN, CONTACT_EMAIL, the About page's name), payments (STRIPE_SECRET_KEY mode test or live, STRIPE_PRICE_PACK and STRIPE_PRICE_REGISTERS present and their `unit_amount` equal to PACK_PRICE_AUD_CENTS and SUBSCRIPTION_PRICE_AUD_CENTS, STRIPE_WEBHOOK_SECRET present, GST_LINE present, STRIPE_FAKE unset), generation (GENERATION_ENABLED true, GENERATION_LIVE 1, ANTHROPIC_API_KEY present, the model id), email (provider configured, sending domain verified, the last test send succeeded, shown with its date, state `set` with no expiry), domain (NEXT_PUBLIC_SITE_URL equals the request's host, the Supabase Site URL and redirect list match, the Stripe webhook endpoint matches), jobs (CRON_SECRET present; the purge, generate and reminders jobs each ran within their schedule), admin (TOTP enrolled for the platform admin), legal (every page in REQ-008 renders with a front-matter `status` that is not `draft`, REQ-008 FR-1's model, so a stable page stays green). The page never prints a value, a key fragment, a price id or an email address; names and states only (REQ-010 FR-2's rule); the CONTACT_EMAIL row says set or unset and never echoes the address.
- FR-2 `scripts/ops/launch-check.mjs --base https://<domain>` runs the subset of FR-1 that is observable from outside without a session (health, the legal pages' status, the CSP, the redirect from the vercel.app name, the price shown on `/pricing` equal to the Stripe-side amount when a read-only Stripe key is given in the environment, the sign-in page's magic-link form), prints one line per check and exits 1 on the first failure; the `/pricing` check never echoes an address. It replaces nothing in `smoke.mjs`; the smoke stays the five-second check, this is the launch check.
- FR-3 Live-mode guards, at boot and in the webhook: a live Stripe key with STRIPE_FAKE set, with a test-mode price id, with a missing webhook secret, or with PACK_PRICE_AUD_CENTS not equal to the live price's `unit_amount` refuses to serve the payment routes (404 with one log line naming the condition) rather than selling at the wrong price; GENERATION_LIVE=1 without an ANTHROPIC_API_KEY refuses the generate job the same way. These extend REQ-007's start-up check; they never refuse the rest of the site. (Delivered as D-2209: the guard records a refusal the payment routes read, instead of stopping the process.)
- FR-4 A `product/ops/LAUNCH.md` checklist, plain numbered steps for Haider, each one naming the dashboard it happens in, the variable it sets, and the FR-1 row that goes green when it is done; the page and the checklist carry the same row names so they can be read side by side.

Session B, transactional email

- FR-5 Provider: `createEmailProvider()` gains the implementation chosen in D-2201, selected by EMAIL_PROVIDER (`log`, the default, or the provider's name); EMAIL_FROM is the sender (`Readyline <no-reply@<domain>>`), the reply-to is CONTACT_EMAIL. The provider sends the register reminders (REQ-018 FR-10) and, once REQ-020 lands, the draft-report reminders (REQ-020 FR-5) and the worker invitation (REQ-020 FR-4), and nothing else; purchase receipts stay with Stripe (REQ-007 FR-7), the app sends none. Every send is one audit-log line with the template name and the hashed address, never the body.
- FR-6 The magic link: Supabase Auth's custom SMTP is pointed at the same provider and sender, so sign-in mail and product mail come from one name; the runbook (FR-4) carries the SPF, DKIM and DMARC records to add at the registrar, and FR-1's email row turns green when a test send from `/admin/launch` ("Send me a test email", to the admin's own address, rate-limited to one a minute) has succeeded, shown with its date, and the provider reports the domain verified.
- FR-7 Templates: plain text with one HTML alternative, no images, no tracking pixels, no links other than to the site, the general-information line in the footer, an unsubscribe line only on the reminders (one click, written to the account's reminder settings; the invitation is transactional and carries none). The unsubscribe link carries a per-account random token stored hashed (SR-6), never the account id. Copy lint runs over the templates.

Session C, the domain

- FR-8 The custom domain is added on Vercel with the vercel.app name kept as an alias that answers 301 to the domain for every path except `/api/*`, which keeps answering on the vercel.app name until the crons and the Stripe webhook endpoint have moved to the domain (then the exclusion goes); NEXT_PUBLIC_SITE_URL, the Supabase Site URL and redirect URLs, the Stripe webhook endpoint, the GitHub PROD_URL variable and the sitemap's base all change in one documented pass (FR-4 lists them), and FR-1's domain row checks each against the request host.
- FR-9 `smoke.mjs` and `launch-check.mjs` run against the domain in the runbook's last step and their output is committed under `product/evidence/req-022/` with the date, once, on the day, never per CI run; the health route reports the domain in `siteUrl` so the record is unambiguous.
- FR-10 HSTS is turned on for the domain only after FR-8 is proven (one deploy later, never the same one), with a one-week max-age first and a one-year max-age after the first week's smoke stays green; the `preload` directive is emitted only at one year and the domain is not submitted to hstspreload.org (that submission is effectively irreversible and is a separate decision for Haider).

Session D, the lawyer's bundle and the business identity

- FR-11 `scripts/ops/legal-bundle.mjs` produces one markdown index under `product/evidence/req-022/legal-bundle-<date>.md` listing, in order, with each entry's URL and "Last updated" date: the five legal pages (REQ-008), the AI and digital tools appendix, the refund promise as it appears on `/pricing` and `/documents`, the pricing page, the sign-in and account-setup screens, the worker invitation and reminder email templates, and one generated sole-trader document set from the committed evidence (`product/evidence/req-005/sole-trader/`, the `.docx` fixtures as committed); the index's head lists the questions in FR-12. No PDF rendering and no headless browser; a reader opens the live pages and the committed files. No customer data of any kind; the bundle is built from the public pages and the committed fixtures only.
- FR-12 `product/legal/questions-for-the-lawyer.md`: the PO writes it (not Dev): the business structure, the general-information disclaimer's adequacy, the refund terms, the subscription terms, the AI disclosure, the privacy policy against the Australian Privacy Principles for a sole trader under the threshold, the worker role and the auditor link, and what a lawyer would change. ## Security and privacy requirements (numbered SR-1 ...)

- SR-1 No page, script, log line, test output or evidence file ever contains a secret value, a key fragment, a price id, a webhook secret or a customer email; FR-1 and FR-2 print names and states only, and a unit test runs the switchboard's renderer over a fake environment full of marker strings, an email-shaped marker among them, and asserts none of them appear in the output.
- SR-2 `/admin/launch` and the test-send action sit behind `requireAdmin()` and the aal2 session; the test send goes only to the signed-in admin's own address and is rate-limited; every view and send is audited (D-418).
- SR-3 The email provider's key is server-only, named in `.env.example`, read in `src/server/**` only. SES delivers bounces and complaints through SNS, not a webhook: at launch they are not configured, and FR-1's email row does not depend on them; if they are configured later, the endpoint verifies the SNS message signature and handles the `SubscriptionConfirmation` handshake before any row changes, and a bounce or complaint marks the address `do_not_send` in the account's reminder settings and nothing else.
- SR-4 The legal bundle is built from committed files and public routes; the script refuses to run when `SUPABASE_SECRET_KEY`, `STRIPE_SECRET_KEY`, `ANTHROPIC_API_KEY`, `CRON_SECRET` or `EMAIL_API_KEY` is set in its environment, or when a `sb-*-auth-token` cookie value is passed to it.
- SR-5 HSTS only after the redirect is proven (FR-10); the CSP and the security headers are unchanged by the domain move and asserted by the smoke on the new name.
- SR-6 The unsubscribe link is a GET that changes state, so it carries a per-account random token of at least 128 bits, stored as its SHA-256 hash and compared in constant time (REQ-020 SR-1's pattern), never the account id; an unknown token answers 404; a click sets `do_not_send` and writes one audit-log line.

## Data (entities, fields, retention)

- `reminder_settings` is a new table, one row per account (`account_id` primary key referencing `accounts`, `do_not_send boolean not null default false`, `do_not_send_reason text` with a CHECK on a short list (`unsubscribed`, `bounce`, `complaint`), `do_not_send_at timestamptz`, `unsubscribe_token_hash text` unique, `created_at`, `updated_at`), with RLS (members read their account's row; the owner updates it; inserts by the owner or the service key; nobody deletes through the API) and explicit grants (D-052). The reminders job reads it before every send; REQ-023 FR-3 and REQ-024 build on it. No other table changes.
- `launch_checks` is not a table: the switchboard reads the environment and the services on request; the ops scripts write their output to `product/evidence/req-022/` as files.

## Dev response

Written 15 Oct 2026 (Dev), before Session A.

1. **The Stripe `unit_amount` check uses the existing restricted key; no new secret.** The key already does this read: `src/lib/payments/price-startup.ts` calls `stripe.prices.retrieve(STRIPE_PRICE_PACK)` at start with a live key and refuses to serve on a mismatch (REQ-007), so the restricted key carries Prices read. FR-1 reuses that call for both price ids (and reads `livemode` from the Price to tell a test id from a live one). FR-2 runs outside the app, so it reads `STRIPE_SECRET_KEY` from the shell environment when present and skips the amount line with "not checked (no key in the environment)" otherwise; it never prints the key or the price id. The one extra permission is for the webhook-endpoint row in FR-1 (`webhookEndpoints.list`, "Webhook Endpoints: read" on the restricted key); until Haider adds it in the dashboard that row reads "unverified" with the sentence saying which permission to add, never an error.
2. **Supabase custom SMTP takes SES SMTP credentials directly; no Auth hook.** Supabase Auth, Authentication → SMTP Settings, takes host, port, username, password and sender; SES issues SMTP credentials from a send-only IAM user (SES console, "Create SMTP credentials"), with host `email-smtp.ap-southeast-2.amazonaws.com` and port 465 (TLS) or 587 (STARTTLS), and the sender must be a verified SES identity (the domain, once its DKIM records are in). Haider enters: the host, the port, the SMTP username and password SES generated (not the IAM access key pair), and `Readyline <no-reply@<domain>>` as the sender. Two vendor facts the runbook must carry: a new SES account is in the sandbox (sends only to verified addresses) until production access is requested, which takes up to a day; and Supabase's rate limit for custom SMTP starts low (30 emails an hour) and is raised in the same settings page. These are from the vendors' documentation as I know it (Supabase "Custom SMTP", AWS "Obtaining SES SMTP credentials"); the runbook step links both and Haider confirms the two pages on the day. The "Send Email" Auth hook is the alternative if the SMTP path ever fails; not needed for a magic link.
3. **HSTS lives in `next.config.ts` `headers()` (static, read at build) and already sends `max-age=63072000; includeSubDomains; preload` on every response, so the vercel.app name carries it today (moot there: Vercel preloads its own domain).** The max-age can be an environment variable (`HSTS_MAX_AGE`, read in `next.config.ts` at build), but on Vercel any environment change takes effect only on the next deployment, so the two-step in FR-10 is two variable edits each followed by a Redeploy click, never a code change; reading it at request time in `proxy.ts` would not remove that redeploy. What Session C delivers: `HSTS_MAX_AGE` with a code default of one week (604800), `preload` added only when the value is at least one year (the preload list requires that), and the runbook's two steps (set 604800 and redeploy after FR-8 is proven; set 31536000 and redeploy a week later). The default moving from two years to one week lowers nothing that matters: no browser has the custom domain pinned yet, and the vercel.app name is preloaded by Vercel regardless.
4. **Estimate.** Session A: 6 to 8 hours (the switchboard's rows as one pure module with the no-secrets test, the admin page, `launch-check.mjs`, the FR-3 guards in the boot check and the webhook route, `LAUNCH.md`), one session plus a short second one for the e2e on three projects. Session B: 4 to 5 hours of code (the SES implementation behind `createEmailProvider()`, EMAIL_PROVIDER/EMAIL_FROM, the templates with the copy lint, the `reminder_settings` table with its RLS, the hashed unsubscribe token and the click, the test send; the SNS endpoint only if the PO configures bounces), plus Haider's account and domain steps, which gate the real test. Session C: 2 to 3 hours of code (the 301 from the vercel.app name with the `/api/*` exclusion, `siteUrl` in the health route, the sitemap base, `HSTS_MAX_AGE`, the evidence capture) plus the runbook pass, which is Haider's. Session D: 2 to 3 hours (the markdown index script, the FR-13 e2e with the two variables set). Order as D-2204. (Vercel Hobby's cron allowance is UNVERIFIED by me: the jobs row assumes the three schedules in `vercel.json`; confirm the plan's limit before relying on it, review finding 11.)

Assumptions for Session A, recorded in `DECISIONS.md` as Dev decisions when built: (a) the three jobs write one `audit_log` row per run (`jobs.<name>.ran`, no actor, the count in `target`) so "ran within its schedule" is a database read, not a log search; (b) the Supabase Site URL and redirect list are not readable with the project's keys, so that row is "unverified" with the sentence naming the dashboard page, and FR-2 proves the redirect from outside instead; (c) the TOTP row reads the platform admin's verified factors through the admin API; (d) the email row's state is an `audit_log` row written by the test-send action, shown with its date and never expiring.
